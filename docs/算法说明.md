# 补帧管线说明

## 一、一次补帧跑的是什么

```
源文件 → probe（样本统计） → 时间轴切段 → N 个 ffmpeg 并行补帧
      → concat 无损拼接 → 回封原音轨 → 核帧数 → 写入相册
```

**1. probe**：`MediaExtractor` 数完视频轨样本，`fps = (counted-1)/span`，`dur = span + 1/fps`，`frames = counted`。容器里的 `frame-rate` 只当兜底，因为它常被写成整数（29.97 → 30），一取整整条时间轴就漂。`rotation` 为 90/270 时交换宽高。

**2. 切段**：第 i 段是 `[dur*i/N, dur*(i+1)/N)` 秒，输出帧数 `round(s1*outFps) - round(s0*outFps)`。段数 `min(8, cores-1)`，再按 `totalOut/24` 与内存上限收紧，4× 时不超过 6。每段内存预算 `250 + 260×百万像素` MB（1080p ≈ 788 MB），可用内存按 `MemAvailable × 0.45` 折算。

**3. 单段命令**（`-ss` 是输入侧 seek，`+2/srcFps` 是给 `tpad` 的余量）：

```
ffmpeg -ss <s0> -t <(s1-s0)+2/srcFps> -i src -an
  -vf "tpad=stop_mode=clone:stop_duration=3/srcFps,
       minterpolate=fps=<outFps>:mi_mode=mci:mc_mode=aobmc:me_mode=bilat:
                    me=epzs:search_param=32:mb_size=16:vsbmc=1:scd=fdiff:scd_threshold=8,
       trim=end_frame=<frames>,setpts=PTS-STARTPTS"
  -r <outFps> -c:v libx264 -preset veryfast -threads 2 -crf 19 -pix_fmt yuv420p
  -progress pipe:1 -nostats c<i>.mp4
```

**4. 拼接**：`-f concat -safe 0 -c copy -an`。全部段都是同一个编码器、同一组参数、同一个时间基，所以拼接不需要重编码，也就不会二次损失。

**5. 回封音轨**：`-map 0:v:0 -map 1:a:0 -c:v copy`，音频三级回退 `copy → aac 160k → 无音轨`。**不加 `-shortest`**：源音轨比画面短时它会把片尾裁掉，看起来像丢帧。

**6. 收尾**：`countFrames` 数一遍成品帧数，写进完成提示；落盘走 MediaStore（Android 10+，`IS_PENDING` 两段式提交），旧系统走 `Movies/ALH Frame` + `scanFile`。

## 二、minterpolate 内部在干什么

`mi_mode=mci`（motion compensated interpolation）分四步：

1. **双向估计**：对前后两帧各算一次块运动矢量，`me=epzs` 是增强预测菱形搜索，`search_param=32` 是搜索半径，`mb_size=16` 是块大小。
2. **双向匹配**（`me_mode=bilat`）：把前向、后向矢量做双向一致性检查，剔掉遮挡区里对不上的矢量。
3. **补偿插帧**（`mc_mode=aobmc`）：按自适应重叠块运动补偿合成中间帧，`vsbmc=1` 再按可变块尺寸细化边界。
4. **场景切换检测**（`scd=fdiff`，阈值 8）：帧间差异超阈值时不做运动补偿，直接退化成混合，避免转场处拖影。

## 三、为什么必须多进程分段

`minterpolate` 基本是单线程的：同一段 720p 素材，`-threads 1` 跑 10148 ms，`-threads 8` 跑 9602 ms，几乎没差别。所以提速只能靠多段进程并发，而不是靠线程数。同理，`-threads 2` 给每段的编码器就够，给多了只是抢 CPU。

## 四、实测数据（1280×720，30→60fps，60 帧真值）

| 做法 | 耗时 | SSIM | PSNR |
| --- | --- | --- | --- |
| 复制帧（dup） | 350 ms | 0.9754 | 30.45 |
| 线性混合（blend） | 389 ms | 0.9758 | 32.96 |
| mci + bidir | 6466 ms | 0.9883 | 36.94 |
| **mci + bilat（当前）** | **3855 ms** | 0.9875 | 36.80 |

`bilat` 比 `bidir` 快 40%，SSIM 只掉 0.0008；4× 档差距更明显：bidir 8214 ms / 0.9692，bilat 5225 ms / 0.9768——又快又准。

其余参数的边际收益很小：`search_param` 32→64 耗时不变、画质不变；`mb_size` 16→8 更慢更差（0.9869）；`mc_mode=obmc` 与 `aobmc` 基本持平（0.9882）。

时间构成：解码 + 编码 370 ms，minterpolate 单独 6638 ms，全流程 11083 ms —— **插值占 85–90%**，1080p 单进程约 240 ms/输出帧。

## 五、块匹配的天花板

四条结构性缺陷，靠调参解决不了：

1. 大位移超搜索半径（`search_param=32` 在 1080p 只覆盖约 2% 画宽）。
2. 旋转、缩放没有对应模型，只能靠分块近似。
3. 遮挡区的双向一致性检查会直接放弃，那里退回混合，出现重影。
4. 光照变化不做补偿，`me` 的块差分会把亮度变化当成运动。

真要往前走，路线是 GPU 光流（Vulkan compute，稠密矢量 + 前后向一致性 + 遮挡掩码 + 软合成）或学习型插值（RIFE 一类）。后者效果好但需要 NCNN/TFLite 级的内核与模型，包体会从 18 MB 涨到 60 MB 以上，且在无 NNAPI 的机型上是纯 CPU 推理，1080p 未必比现在快。

## 六、已知限制

- **VFR 源**：时间轴按平均帧率算，VFR 素材的段边界会有毫秒级误差，输出仍严格 CFR。
- **4× 高帧率**：30 fps 源 4× 得 120 fps，H.264 能编，但很多播放器/相册会按 60 fps 显示，看起来像没补够。这是容器与播放端的问题，不是文件问题。
- **10-bit 源**：输出固定 `yuv420p`，HDR/10-bit 素材会掉到 8-bit。

## 七、ALH Frame Standard 自研内核

Standard 走的是另一条路：不调 ffmpeg 的插值滤镜，用自带内核 `alhift` 直接吃 YUV 帧、吐补好的 YUV 帧，ffmpeg 只负责解码和编码。内核源码在 [native/alhift.cpp](../native/alhift.cpp)，接口与选项表见 [native/README.md](../native/README.md)。

管线（每段）：

```
ffmpeg -ss .. -t .. -i src -an -f rawvideo -pix_fmt yuv420p -   # 解码
  | alhift - W H 帧数 - 倍率 选项                                # 补帧
  | ffmpeg -f rawvideo -s WxH -r <outFps> -i - ... -f mpegts out.ts   # 编码
```

内核做五件事：金字塔块匹配（8×8 SAD，粗到细，最细层半径 8）、矢量场中值滤波、OBMC 4-tap 重叠加权、按匹配代价算逐像素可信度再合成、可选的去重复帧与场景切换检测。

和 `minterpolate` 的差别在合成阶段：`minterpolate` 的 `ADD_PIXELS` 永远按 (1−α)/α 做加权平均，没有遮挡分支；`alhift` 会先看两侧匹配代价，一侧明显更可信时压低另一侧权重，因此前景盖背景的边界不会糊成双层。

实测（真实拍摄 foreman 352×288 15→30fps，只比插值帧）：`minterpolate` 0.9478 SSIM，`alhift` 现行默认配置 0.9524。720p 干净合成片 0.9870 对 0.9864、加噪片 0.8094 对 0.7838，耗时 13.1 s 对 14.4 s。低分辨率合成素材上 0.9907 对 0.9864，且快一倍。

代价函数是差距的主要来源：块匹配用块外扩 2 像素的 12×12 窗算 SAD，再按 `pen×(|dx|+|dy|)` 惩罚位移；`pen` 由首帧拉普拉斯响应估噪声自动定，干净片 0.25、噪声越大越松（下限 0.02）。核心结论和 ffmpeg 那份源码一致：更好的代价函数比更彻底的搜索管用。

代价：720p 单路比 `minterpolate` 略省（12.4 s 对 14.4 s/30 对帧），1080p 以上两边的差距会随分辨率放大——大位移镜头里 8×8 块更容易找错矢量，这是当前主要短板。
